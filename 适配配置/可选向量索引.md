# 可选向量索引（HNSW / sqlite-vec）

> 默认不装、不启用：Membrane 开箱仍然用内置零依赖 LSH 桶索引。
> 本页只写给"数据量大、想要 ANN 级查询"的人。

## 什么时候需要

- 记忆量在**百万级以上**，LSH 的候选扫描开始成为瓶颈；
- 能接受多装一个可选包/扩展，并自己承担它的原生依赖；
- 想对比 HNSW / sqlite-vec 与默认 LSH 的召回和延迟。

如果只是几万到十几万条，先用默认 LSH（10 万 × 1536 维实测纯向量约 300ms），不必上 ANN。

## 统一接法：注入一个 `VectorIndex`

```ts
import { Membrane, HnswVectorIndex } from "membrane-memory";

const vectorIndex = new HnswVectorIndex({
  dim: 1536,
  maxElements: 200_000, // 满了会自动扩容
});

const m = new Membrane({
  dbPath: "./memory.db",
  vectorIndex,
});
```

写入/删除会自动同步到适配器；首次查询时，适配器会从 `embeddings` 表全量重建一次，
所以**不需要手动导入旧数据**。

## HNSW 适配器

```bash
npm install hnswlib-node
```

- 构造时才会 `require("hnswlib-node")`；没装会抛 `E_VECTOR_INDEX_UNAVAILABLE`，不会影响默认路径。
- 当前用 `cosine` 空间；适配器只返回候选 id，最终余弦排序仍由 Membrane 做。
- 大量删除后 HNSW 的 tombstone 会占内存，建议定期重建（清空后由 Storage 自动重建）。

## sqlite-vec 适配器

```bash
npm install sqlite-vec
```

或者自己准备 vec0 动态库：

```ts
import { SqliteVecVectorIndex } from "membrane-memory";

const vectorIndex = new SqliteVecVectorIndex({
  dim: 1536,
  extensionPath: "C:/path/to/vec0.dll", // 不传则尝试 npm 包 sqlite-vec
});
```

- 索引放在独立的**内存 SQLite**里，不碰主库；扩展崩了不会污染 `memory.db`。
- 主库仍是 `node:sqlite` 的普通表；重启后从 `embeddings` 重建。

## 自定义适配器

实现 `VectorIndex` 五个方法即可：

```ts
interface VectorIndex {
  readonly name: string;
  upsert(id: string, vec: Float32Array): void;
  remove(id: string): void;
  search(queryVec: Float32Array, limit: number): string[] | null;
  size(): number;
  clear?(): void;
  close?(): void;
}
```

约定：

- `search` 返回 `null` = 适配器不可用，Membrane 回退 LSH；
- 返回 `[]` = 适配器可用但确实没候选，Membrane 返回空结果，**不会偷偷全扫**；
- 抛出异常 = 本进程标记适配器失败，后续查询回退 LSH，写入不受影响。

## 边界

- 适配器只负责"缩小候选"，不改变 RRF 融合权重；近似索引的分数不会直接进排序。
- 外部索引是**进程内**的；多进程同时写同一个 `memory.db` 时，各自维护自己的索引，重启后重建。
- `HnswVectorIndex` / `SqliteVecVectorIndex` 都没有进 `dependencies`；`npm install membrane-memory` 不会下载任何原生二进制。
